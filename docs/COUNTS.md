# How StreetCred computes the counts it displays

This file is the derivation of every number on this site that claims to be a count
of something that happened at a street corner. It exists so that a disagreement
about one of those numbers can be settled by reading a query rather than by
arguing about intent.

It explains. It does not correct. No displayed number changed when this file was
written, and nothing here is a proposal to change one.

The immediate occasion is a real discrepancy. At 6th and Mission, this site can be
made to say the severe-injury count is 9 and can be made to say it is 11. Both are
true. They are answers to two different questions asked over two different circles,
on purpose, and section 6 proves that with output from the city's own API.

Measured at **2026-08-19 22:48 PT (2026-08-20 05:48 UTC)**. Every number below was
produced by a command run at that time, against `data.sfgov.org` and against the
live Worker. The collision dataset moves when the city republishes it and the time
windows slide every second, so a re-run tomorrow will differ slightly. The queries
are the durable part. The numbers are a snapshot.

---

## 1. The three datasets

Everything counted here comes from three keyless, free, public DataSF resources.
There is no private source, no scrape, and no model anywhere in the counting path.

| Role | Resource id | Title | Link |
|---|---|---|---|
| Collisions | `ubvf-ztfx` | Traffic Crashes Resulting in Injury | https://data.sfgov.org/d/ubvf-ztfx |
| 311 reports | `vw6y-z8j6` | 311 Cases | https://data.sfgov.org/d/vw6y-z8j6 |
| Intersection geometry | `gmfx-8h6i` | Street Intersections | https://data.sfgov.org/d/gmfx-8h6i |

`gmfx-8h6i` is not counted from. It supplies the latitude and longitude that the
circles in sections 3 and 4 are centered on, via `src/resolve.js`. Its shape is
one row per street leg, so a single intersection is two or three rows sharing a
`cnn` and an identical point.

Freshness of the collision dataset at measurement time:

```
$ curl -s -G "https://data.sfgov.org/resource/ubvf-ztfx.json" \
    --data-urlencode '$select=max(data_as_of) as d, min(collision_datetime) as earliest, max(collision_datetime) as latest'
[{"d":"2026-07-27T00:00:00.000","earliest":"2005-01-01T01:15:00.000","latest":"2026-06-30T21:48:00.000"}]
```

The dataset reaches back to 2005 and, as published on 2026-07-27, its most recent
collision is dated 2026-06-30. Every window described below is a window into that
record, not into the present. A count of the "last five years" ends wherever the
city's reporting lag ends.

## 2. Machinery shared by every count

**One query builder, one receipt.** `src/resolve.js` exposes `soqlUrl(dataset, params)`
and `soql(dataset, params)`. `soql` fetches exactly the URL `soqlUrl` builds. Every
provenance link the site prints is generated by `soqlUrl` from the same parameter
object the fetch used, so a receipt cannot describe a query the page did not run.
This is the property that makes the rest of this file checkable.

**The geographic predicate is always a circle.** Every count uses Socrata's
`within_circle(point, lat, lon, radius_m)` against the dataset's own `point`
column. There is no polygon, no bounding box, no street-segment join, and no
buffer of a line. The radius is the only geographic parameter, and the whole of
section 6 turns on which radius a given lane passes.

**Time windows are computed at query time in UTC, from 365-day years.** In
`src/score.js`:

```js
const yearsAgo = (n) =>
  new Date(Date.now() - n * 365 * 24 * 3600 * 1000).toISOString().slice(0, 19);
```

`src/index.js` builds its windows the same way inline. Three consequences worth
stating rather than hiding:

- A "5 year" window is 1825 days, not five calendar years. It drifts against the
  calendar by about one day per leap year.
- The boundary is recomputed on every request, so it slides continuously. Two
  identical requests seconds apart use two different literals.
- `Date.toISOString()` produces UTC, and `collision_datetime` is a floating
  timestamp with no zone. At the boundary the comparison is therefore off by the
  UTC offset, about 7 hours. This affects only collisions dated within hours of
  the exact five-year mark.

The comparison is always strict (`>`), never `>=`.

**The severity vocabulary is four literal strings.** `collision_severity` in
`ubvf-ztfx` takes exactly four values citywide:

```
$ curl -s -G "https://data.sfgov.org/resource/ubvf-ztfx.json" \
    --data-urlencode '$select=collision_severity,count(*)' \
    --data-urlencode '$group=collision_severity'
[{"collision_severity":"Fatal","count":"622"}
,{"collision_severity":"Injury (Complaint of Pain)","count":"41829"}
,{"collision_severity":"Injury (Other Visible)","count":"18715"}
,{"collision_severity":"Injury (Severe)","count":"4638"}]
```

`src/score.js` matches on those strings by exact equality, never by substring or
prefix:

```js
fatal:        bySeverity["Fatal"] || 0,
severe:       bySeverity["Injury (Severe)"] || 0,
otherVisible: bySeverity["Injury (Other Visible)"] || 0,
pain:         bySeverity["Injury (Complaint of Pain)"] || 0,
```

The word "severe" on this site always and only means the literal DataSF value
`Injury (Severe)`. It never means "severe or fatal", and it never means a
judgment call made by this site. Note also that `ubvf-ztfx` contains only
injury collisions, so a property-damage-only crash is absent from every count
here. There is no "Property Damage Only" bucket to exclude.

**There is no dedup rule, because one row is one collision record.** The site
applies no deduplication of any kind. That is a deliberate non-decision, and it
is defensible because the dataset is already one row per collision. Checked at
the corner in question:

```
$ curl -s -G "https://data.sfgov.org/resource/ubvf-ztfx.json" \
    --data-urlencode '$select=count(*) as rows, count(distinct unique_id) as ids' \
    --data-urlencode "\$where=within_circle(point, 37.780971, -122.408709, 150) AND collision_datetime > '2021-08-21T05:46:50'"
[{"rows":"94","ids":"94"}]
```

94 rows, 94 distinct `unique_id`. The same query against `case_id_pkey` also
returns 94. Rows are not per-party or per-victim, so a two-car collision that
injured four people is one row and counts once. This also means the counts are
counts of *collisions*, not of *people harmed*. `number_killed` is the one place
the site counts people instead of records, and it is called out in section 4.2.

**311 is filtered by an explicit allow list, never a substring.** `SERVICE_NAMES`
in `src/data.js`:

```
Street Defects, Street Defect, Sign Repair, Streetlights, Sidewalk or Curb,
Sidewalk and Curb, Blocked Street or SideWalk, Blocked Street and Sidewalk,
Color Curb
```

The comment above it records why: an earlier substring match on "Street" swept in
Street and Sidewalk Cleaning, a sanitation queue, and inflated one corner from 354
to 8,546. The list is shared by the score lane and the stats lane, imported rather
than copied.

## 3. The Danger Index counts (80 meters)

Source: `src/score.js`, functions `scoreQueries()` and `countsFor()`.
Displayed on: every corner page's grade, the citywide index, `/api/score`.

The radius constant is declared once and exported:

```js
// src/score.js line 13
export const SCORE_RADIUS = 80;
```

Its comment states the reason directly: "Tighter than the 150m the stats lane
uses. A score is a claim about one intersection, not about a block in every
direction."

### 3.1 Severity counts

- Dataset: `ubvf-ztfx`
- Predicate: `within_circle(point, lat, lon, 80)`, radius from `SCORE_RADIUS` in `src/score.js`
- Window: `collision_datetime > (now - 5 years)`, 1825 days, computed per request
- Severity field: `collision_severity`, grouped, matched against the four literals in section 2
- Dedup: none, one row is one collision

Query shape:

```
$select = collision_severity,count(*)
$where  = within_circle(point, {lat}, {lon}, 80) AND collision_datetime > '{now-5y}'
$group  = collision_severity
```

Runnable, at 6th and Mission:

```bash
SINCE=$(python3 -c "import datetime;print((datetime.datetime.utcnow()-datetime.timedelta(days=5*365)).strftime('%Y-%m-%dT%H:%M:%S'))")
curl -s -G "https://data.sfgov.org/resource/ubvf-ztfx.json" \
  --data-urlencode '$select=collision_severity,count(*)' \
  --data-urlencode "\$where=within_circle(point, 37.780971, -122.408709, 80) AND collision_datetime > '$SINCE'" \
  --data-urlencode '$group=collision_severity'
```

Output at 2026-08-19 22:48 PT:

```json
[{"collision_severity":"Injury (Complaint of Pain)","count":"38"}
,{"collision_severity":"Injury (Other Visible)","count":"15"}
,{"collision_severity":"Injury (Severe)","count":"9"}]
```

A severity with no rows is simply absent from the grouped result, which is why
`countsFor` reads each bucket with `|| 0`. There is no `Fatal` row here, so
`fatal` is 0.

### 3.2 Pedestrian-involved count

Same dataset, same circle, same window, with one extra clause:

```
$select = count(*)
$where  = within_circle(point, {lat}, {lon}, 80)
          AND collision_datetime > '{now-5y}'
          AND ped_action not in('No Pedestrian Involved','Not Stated')
```

The field is `ped_action`. SoQL `not in` drops null rows, so a collision with no
recorded `ped_action` is not counted. This is an intentional match to the local
sweep, which reproduces the same test in JavaScript.

```bash
curl -s -G "https://data.sfgov.org/resource/ubvf-ztfx.json" \
  --data-urlencode '$select=count(*)' \
  --data-urlencode "\$where=within_circle(point, 37.780971, -122.408709, 80) AND collision_datetime > '$SINCE' AND ped_action not in('No Pedestrian Involved','Not Stated')"
```

Output: `[{"count":"28"}]`

Note that this count overlaps the severity counts. A pedestrian collision is
counted once in its severity bucket and again here, and the scoring weights
(`ped: 2`) are calibrated on that basis. It is a modifier, not a fifth category.

### 3.3 Street-condition 311 count

- Dataset: `vw6y-z8j6`
- Predicate: `within_circle(point, lat, lon, 80)`, the same 80m circle
- Window: `requested_datetime > (now - 1 year)`, 365 days
- Filter: `service_name in(...)`, the nine literals in section 2
- Dedup: none

```
$select = count(*)
$where  = within_circle(point, {lat}, {lon}, 80)
          AND requested_datetime > '{now-1y}'
          AND service_name in('Street Defects','Street Defect','Sign Repair',
              'Streetlights','Sidewalk or Curb','Sidewalk and Curb',
              'Blocked Street or SideWalk','Blocked Street and Sidewalk','Color Curb')
```

```bash
SINCE1=$(python3 -c "import datetime;print((datetime.datetime.utcnow()-datetime.timedelta(days=365)).strftime('%Y-%m-%dT%H:%M:%S'))")
curl -s -G "https://data.sfgov.org/resource/vw6y-z8j6.json" \
  --data-urlencode '$select=count(*)' \
  --data-urlencode "\$where=within_circle(point, 37.780971, -122.408709, 80) AND requested_datetime > '$SINCE1' AND service_name in('Street Defects','Street Defect','Sign Repair','Streetlights','Sidewalk or Curb','Sidewalk and Curb','Blocked Street or SideWalk','Blocked Street and Sidewalk','Color Curb')"
```

Output: `[{"count":"79"}]`

The stored score for this corner carries `safety311: 78`. That is not a
discrepancy in the query. It is a cached score computed on an earlier day against
a 365-day window that has since slid forward by one report. Section 5 covers how
cached and live figures are labelled.

Reminder from `src/score.js`: this input is capped at 8 points
(`MAINTENANCE_CAP`), which is less than one fatality. A 311 report is paperwork
and is never allowed to outweigh a person.

## 4. The stats-tile counts (150 meters)

Source: `getStats()` in `src/index.js`, around line 199.
Displayed on: the corner page's statistic tiles, the letter's cited counts, the
press context, `/api/stats` for any corner not in the SCORED tier.

The radius here is not a module constant. It is `c.radiusMeters`, a per-corner
field, and every corner in the repo carries `radiusMeters: 150`: both entries in
`CORNERS` in `src/data.js`, and `makeCorner()` for any corner resolved at runtime.

The payload states its own radius and window, so a tile cannot be read without
them:

```json
{"source":"live","radiusM":150,"reports311Window":"3 years", ...}
```

### 4.1 `crashes`

- Dataset: `ubvf-ztfx`
- Predicate: `within_circle(point, lat, lon, 150)`
- Window: `collision_datetime > (now - 5 years)`, the same 1825 days as the score
- Severity: **none**. This is `count(*)` over all rows, every severity together.
  Because `ubvf-ztfx` is injury-only, that is the same thing as the sum of the
  four severity buckets.
- Dedup: none

```
$select = count(*)
$where  = within_circle(point, {lat}, {lon}, 150) AND collision_datetime > '{now-5y}'
```

```bash
curl -s -G "https://data.sfgov.org/resource/ubvf-ztfx.json" \
  --data-urlencode '$select=count(*)' \
  --data-urlencode "\$where=within_circle(point, 37.780971, -122.408709, 150) AND collision_datetime > '$SINCE'"
```

Output: `[{"count":"94"}]`

### 4.2 `fatal`

This is the one count of people rather than records.

```
$select = sum(number_killed)
$where  = within_circle(point, {lat}, {lon}, 150) AND collision_datetime > '{now-5y}'
```

```bash
curl -s -G "https://data.sfgov.org/resource/ubvf-ztfx.json" \
  --data-urlencode '$select=sum(number_killed)' \
  --data-urlencode "\$where=within_circle(point, 37.780971, -122.408709, 150) AND collision_datetime > '$SINCE'"
```

Output: `[{"sum_number_killed":"0"}]`

Two things follow. First, this figure is a sum of a per-collision victim count,
so it can legitimately exceed the number of `Fatal` rows. Second, it is not the
same quantity as the score's `fatal` input, which is a count of rows whose
`collision_severity` equals `Fatal` inside the 80m circle. The two can differ by
radius and by units at once.

### 4.3 `reports311`

- Dataset: `vw6y-z8j6`
- Predicate: `within_circle(point, lat, lon, 150)`
- Window: `requested_datetime > (now - 3 years)`, 1095 days. **Three years here,
  one year in the score.** The payload carries `reports311Window: "3 years"` for
  exactly this reason.
- Filter: the same nine `SERVICE_NAMES`

```bash
SINCE3=$(python3 -c "import datetime;print((datetime.datetime.utcnow()-datetime.timedelta(days=3*365)).strftime('%Y-%m-%dT%H:%M:%S'))")
curl -s -G "https://data.sfgov.org/resource/vw6y-z8j6.json" \
  --data-urlencode '$select=count(*)' \
  --data-urlencode "\$where=within_circle(point, 37.780971, -122.408709, 150) AND requested_datetime > '$SINCE3' AND service_name in('Street Defects','Street Defect','Sign Repair','Streetlights','Sidewalk or Curb','Sidewalk and Curb','Blocked Street or SideWalk','Blocked Street and Sidewalk','Color Curb')"
```

Output: `[{"count":"436"}]`

### 4.4 `district`

Not a displayed count, but it decides which Supervisor a letter is addressed to,
so its derivation belongs here.

```
$select = supervisor_district,count(*)
$where  = within_circle(point, {lat}, {lon}, 150)
$group  = supervisor_district
```

No time bound: this is a geographic vote, and more rows make it steadier.

```bash
curl -s -G "https://data.sfgov.org/resource/ubvf-ztfx.json" \
  --data-urlencode '$select=supervisor_district,count(*)' \
  --data-urlencode '$where=within_circle(point, 37.780971, -122.408709, 150)' \
  --data-urlencode '$group=supervisor_district'
```

Output: `[{"supervisor_district":"6","count":"355"}]`

It is grouped rather than `$limit 1` because a major street is often a district
boundary. The comment in `src/index.js` records the case that forced this: within
150m of 6th and Market, DataSF holds 242 rows in District 6 and 114 in District 5,
so a single arbitrary row picks the wrong Supervisor and nothing on the page looks
broken. `districtFromRows()` in `src/resolve.js` additionally refuses to name a
district when the runner-up is within 90 percent of the leader, returning null so
the letter is addressed citywide instead of confidently to the wrong person.
Parsing note carried in both files: collisions return `"11"` while 311 returns
`"9.00000"`, so every read is `parseInt`.

## 5. The third lane: swept counts at 80 meters

A corner in the SCORED tier, meaning one that has been graded by the citywide
sweep but never audited live, does not run any of the queries above on request.
`/api/stats` returns `cityStats()` from `src/city.js`, built from the stored shard
row. Its shape differs in three ways that matter:

| | live lane (section 4) | sweep lane |
|---|---|---|
| `source` | `"live"` | `"sweep"`, with `asOf` |
| `radiusM` | 150 | 80 |
| `crashes` | `count(*)` of all rows | sum of the four severity buckets |
| `reports311Window` | `"3 years"` | `"12 months"` |

Observed live, 2026-08-19 22:48 PT:

```
$ curl -s "https://streetcred.thealexschroeder.workers.dev/api/stats?x=clay-and-drumm"
{"source":"sweep","asOf":"2026-08-18","radiusM":80,"crashes":3,"fatal":0,
 "reports311":5,"reports311Window":"12 months","district":3, ...}

$ curl -s "https://streetcred.thealexschroeder.workers.dev/api/stats?x=6th-and-mission"
{"source":"live","radiusM":150,"reports311Window":"3 years","crashes":94,
 "fatal":0,"reports311":436,"district":6, ...}
```

The swept figures are not a live query and not a sample. They are real counts,
true as of the sweep date, and the page tags them with that date rather than with
the word sample. `tools/sweep.mjs` computes them by bulk-downloading the three
datasets and bucketing every row into a 100m grid, then applying an
equirectangular distance test with `RADIUS_M = 80`, which the file annotates as
"SCORE_RADIUS. The grade's footprint, per src/score.js." It imports `pointsFor`
and `SERVICE_NAMES` from `src/` rather than restating them, so the census cannot
drift from production arithmetic.

Practical consequence for anyone diffing this site against its own API: **a
`crashes` figure of 94 and a `crashes` figure of 3 may both be correct and are
not comparable.** Read `source` and `radiusM` off the payload before comparing
two corners.

## 6. Reconciliation: 9 and 11 at 6th and Mission

This is the section the file exists for.

Corner: 6th and Mission, San Francisco. Coordinates as the site resolves them,
`lat 37.780971, lon -122.408709`. Window: five years, `collision_datetime >
'2021-08-21T05:46:36'` at the moment of measurement.

### 6.1 Full severity breakdown at both radii

Both rows come from the query in section 3.1 with only the radius changed.

| `collision_severity` | 80m (Danger Index) | 150m (stats tiles) |
|---|---|---|
| Fatal | 0 (bucket absent) | 0 (bucket absent) |
| Injury (Severe) | **9** | **11** |
| Injury (Other Visible) | 15 | 22 |
| Injury (Complaint of Pain) | 38 | 61 |
| **Total rows** | **62** | **94** |

Raw output at 80m:

```json
[{"collision_severity":"Injury (Complaint of Pain)","count":"38"}
,{"collision_severity":"Injury (Other Visible)","count":"15"}
,{"collision_severity":"Injury (Severe)","count":"9"}]
```

Raw output at 150m:

```json
[{"collision_severity":"Injury (Complaint of Pain)","count":"61"}
,{"collision_severity":"Injury (Other Visible)","count":"22"}
,{"collision_severity":"Injury (Severe)","count":"11"}]
```

### 6.2 The totals close exactly

61 + 22 + 11 = **94**, and 94 is precisely what `/api/stats` reports as `crashes`
for this corner, and precisely what `count(*)` over the same circle and window
returns:

```
$ curl -s -G "https://data.sfgov.org/resource/ubvf-ztfx.json" \
    --data-urlencode '$select=count(*)' \
    --data-urlencode "\$where=within_circle(point, 37.780971, -122.408709, 150) AND collision_datetime > '$SINCE'"
[{"count":"94"}]

$ curl -s "https://streetcred.thealexschroeder.workers.dev/api/stats?x=6th-and-mission"
{"source":"live","radiusM":150, ... "crashes":94, ...}
```

38 + 15 + 9 = **62**, and `count(*)` over the 80m circle returns 62. The score's
own stored counts for this corner are
`{"fatal":0,"severe":9,"otherVisible":15,"pain":38,"ped":28,"safety311":78}`,
served by `/api/score?x=6th-and-mission`. The first four sum to 62.

Nothing is missing and nothing is double-counted in either lane. The two circles
are nested, the larger one contains the smaller one, and the differences are the
rows in the annulus between 80m and 150m.

### 6.3 Severe count as a function of radius

Same query, same window, five radii. If the 9 and the 11 were a bug, this column
would jump. It does not: it climbs monotonically, the way a count inside a growing
circle has to.

| radius | Fatal | Severe | Other Visible | Complaint of Pain | total rows |
|---:|---:|---:|---:|---:|---:|
| 50m | 0 | 2 | 8 | 19 | 29 |
| **80m** | 0 | **9** | 15 | 38 | **62** |
| 100m | 0 | 9 | 16 | 39 | 64 |
| **150m** | 0 | **11** | 22 | 61 | **94** |
| 200m | 2 | 13 | 37 | 95 | 147 |

Reproduce the whole table:

```bash
SINCE=$(python3 -c "import datetime;print((datetime.datetime.utcnow()-datetime.timedelta(days=5*365)).strftime('%Y-%m-%dT%H:%M:%S'))")
for R in 50 80 100 150 200; do
  echo "--- radius ${R}m ---"
  curl -s -G "https://data.sfgov.org/resource/ubvf-ztfx.json" \
    --data-urlencode '$select=collision_severity,count(*)' \
    --data-urlencode "\$where=within_circle(point, 37.780971, -122.408709, $R) AND collision_datetime > '$SINCE'" \
    --data-urlencode '$group=collision_severity'
  echo
done
```

Two features of that table are worth naming. Between 80m and 100m the severe
count does not move at all, which is what a genuine spatial distribution looks
like: severe collisions are not spread evenly, they sit at specific points. And
at 200m two `Fatal` rows appear that neither displayed lane counts, which is a
concrete illustration of what a wider circle would sweep in. 200m from 6th and
Mission reaches most of the way to 5th and to 7th. A grade computed there would
be a grade of the neighborhood, not of the crossing.

### 6.4 Which number answers which question

State it plainly, because this is the sentence the discrepancy needs.

- **11 is the correct answer to "how many severe injuries were recorded within
  150 meters of 6th and Mission in the last five years".** It is what the stats
  tiles, the letter, and `/api/stats` are describing: the corner's surroundings.
- **9 is the correct answer to "how many severe injuries does the Danger Index
  count at 6th and Mission".** It is what the grade is computed from, over the
  80m circle declared as `SCORE_RADIUS` in `src/score.js`, because a score is a
  claim about one intersection.
- **Neither is wrong, and neither is a correction of the other.** They differ by
  the radius and by nothing else. Same dataset, same five-year window, same
  literal `Injury (Severe)` match, same absence of dedup, same `within_circle`
  predicate. Change 80 to 150 in one query string and 9 becomes 11.

The site already says this in three places rather than one: the payload carries
`radiusM`, the tiles print "within Nm", and the letter-generation prompt in
`src/index.js` instructs that the first citation of the 150m count must state in
the same sentence that the Danger Index grade is computed over a tighter 80 meter
core "so the two figures are measured over different areas and a reader should not
expect them to reconcile."

## 7. Counts that are not collision counts

Two figures on the site are counts of the site's own work rather than of the
city's record. They are included so a reader does not go looking for a SoQL query
behind them.

- **"7,355 SF intersections scored"** in the masthead reads `totalScored` from the
  `city:meta` record in KV, written by the citywide sweep. Confirmed live at
  measurement time: `/api/city` returns `"total":7355` with `"sweepDate":"2026-08-18"`.
  Note an unresolved difference: the sweep artifact on disk, `sweep-results.json`,
  carries `runDate 2026-08-18`, `radiusM 80`, and 7,353 corners with nonzero
  points. This file does not establish where the remaining 2 come from, and says
  so rather than guessing. Separately, the score's `sampleSize` is 8,254, which is
  the full census of crossings including those with zero points; the published
  roster is the nonzero subset.
- **The audited roster** at measurement time: `/api/board` returns `count 24`,
  of which 23 render as fully AUDITED and one, 1st-and-bush, renders ENRICHED
  because its imagery lane came back partial on the 2026-08-19 daily audit. The
  tier vocabulary is AUDITED / ENRICHED / SCORED, with a separate PRESS-CHECKED
  marker that does not change tier.

## 8. Known limits of the counting method

Stated here so a watchdog does not have to discover them.

1. **No exposure normalization.** The index ranks reported harm, not risk per
   crossing. A busy corner with many crossings and a quiet one with few are ranked
   on raw counts. This sentence travels with the score everywhere as
   `SCORE_CAVEAT` in `src/score.js`.
2. **Overlapping circles.** Adjacent crossings within 80m of each other share
   collisions, so a dense block produces several corners each counting the same
   rows. `src/methodology.js` names this as a known limitation.
3. **Reporting lag.** Counts describe what the city has published, not what
   happened. As of 2026-07-27 the dataset's most recent collision is 2026-06-30.
   A "five year" count is effectively missing its most recent weeks.
4. **Injury-only dataset.** `ubvf-ztfx` excludes property-damage-only collisions
   entirely. Near-misses, unreported collisions, and crashes police did not record
   are outside every number here.
5. **365-day years and a UTC boundary.** See section 2. Sub-day precision at the
   window edge is not meaningful.
6. **Cached figures drift from live ones.** A stored score carries the counts as
   of when it was computed, and its sliding windows have moved since. Section 3.3
   shows a live 79 against a stored 78. Read `source` and `asOf` before comparing.
